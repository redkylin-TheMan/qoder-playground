## 三、发现并修复的 Bug（阻塞 P0）

### 3.1 现象

粮食出库作废（无论 R3 未收款 还是 R2 已收款）一律报错：

```
success=false, message=执行数据库异常,违反了完整性例如：违反惟一约束...
```

实际后端日志：`ORA-02290: 违反检查约束条件 (CRM_SALE1.CK_DCF_BIZ_TYPE)`。

### 3.2 根因

文件：`liangyizhilian-be/hl-drying/.../CustomerAccountServiceImpl.java`

这个类里有**两个 `@PostConstruct` 启动迁移方法**，都 `DROP + ADD` 同一个 check 约束 `CK_DCF_BIZ_TYPE`，但**枚举列表不一致**：

1. `autoMigrateV22FinanceReview()` — V2.2 列表，含 `grain_out_void` 等 4 个新值
2. `autoMigrateAgriPrepaid()` — T-125 列表，**不含**这 4 个新值

`@PostConstruct` 执行顺序由 Spring 决定（不稳定）。本次启动恰好是「V2.2 先跑 → T-125 后跑」，T-125 用旧列表重建约束，**把 V2.2 扩的 `grain_out_void` 等又踢掉了**。结果作废写 `grain_out_void` 流水时触发 ORA-02290。

> 连带影响：T-140 收款单的 `pre_collect/pre_collect_use/pre_collect_void` 也会被 T-125 踢丢（收款单预收功能同样受影响）。

### 3.3 修复

把两处 Java 迁移的约束列表**统一为全集**（V2.2 的 4 个 void + T-125 已有 + T-140 的 pre_collect 三件套 + input_return_void）。

- `CustomerAccountServiceImpl.java` 第 66–86 行（T-125 `autoMigrateAgriPrepaid`）
- `CustomerAccountServiceImpl.java` 第 229–249 行（V2.2 `autoMigrateV22FinanceReview`）

这样无论 `@PostConstruct` 执行顺序如何，最终约束都是完整的。**已重启生效**。

### 3.4 ⚠️ 留给后续的系统性隐患

同一个 `CK_DCF_BIZ_TYPE` 约束在 **4 个地方**各自维护一份列表，互相 DROP+ADD 覆盖：

| # | 位置 | 列表 |
|---|---|---|
| 1 | Java `autoMigrateAgriPrepaid` | 已修为全集 |
| 2 | Java `autoMigrateV22FinanceReview` | 已修为全集 |
| 3 | SQL `V20260611_T125_agri_prepaid.sql` | 旧（缺 void + pre_collect） |
| 4 | SQL `V20260619_T140_drying_receipt.sql` | 旧（缺 void + input_return_void） |

SQL 脚本是**手动执行**的（非自动迁移），如果将来有人在干净库上重跑这些脚本，约束又会回退。**建议后续把 bizType 枚举收口到单一来源**，否则每加一个 bizType 都要同步改 4 处。

## 五、触发器与溯源机制（V2.2 基础设施）

本次测试涉及的后端"留痕"机制，**全部自动触发，业务代码不用手写日志**：

### 5.1 库存流水触发（TBL_DRYING_STOCK_LOG）

- **机制**：所有改库存的操作（新建/编辑/盘点/删除/作废/改单）统一走 `IStockChangeService` 入口，自动写一条流水
- **字段**：`biz_type`（outbound/inbound/outbound_void/outbound_edit 等）、`qty_before`、`qty_change`、`qty_after`、`ref_bill_id`
- **验证**：本测试改净重时，自动出了 `outbound_edit Δ+20` 的流水（见 4.3 ②）

### 5.2 字段变更溯源触发器（TBL_DRYING_CHANGE_LOG）🔥 V2.2 新增

- **机制**：9 个 Oracle 触发器挂在 4 张业务单 + 相关表上。任何 UPDATE 触发时，触发器从 SESSION 的 `CLIENT_INFO` 读取**操作原因/单号/操作人**，把字段旧值→新值写到 `TBL_DRYING_CHANGE_LOG`
- **CLIENT_INFO 写入**：业务方法调用前 `DryingClientInfoUtil.setClientInfo(原因, 单号, 操作人)` 写到 Oracle SESSION，触发器读取；方法结束 `clearClientInfo()` 清理（防误记）
- **查询**：`/hl-drying/drying/change-log/list?bizNo=CK...`（见 4.2），或前端"操作日志"页
- **验证**：本次财务退款时，代码里 `markReviewed` 前 `setClientInfo("财务核查:grain_out ...")`，触发器会记下这次状态变更

### 5.3 财务通知触发（TBL_DRYING_NOTICE）

- **机制**：R2 场景（已收付款）作废/改单时，业务层自动写一条 `CAT=FINANCE, LEVEL=IMPORTANT` 的通知给财务角色
- **查询**：`/hl-drying/drying/notice/list?factoryId=...`，或前端"通知中心"

### 5.4 财务待办聚合（实时计算，非落表）

- **机制**：`/finance/todo/list` 实时聚合 4 张业务单 + 收付款单里 `finance_review_status=pending_review`（或 status=pending_review）的行
- **统计**：`/finance/todo/stat` 返回红点数 + 按 billType/action 分桶
- **验证**：R2 作废后红点+1，财务退款后清零（本测试已验证）
